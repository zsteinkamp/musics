# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What is Musics

A simple music browser/streamer. NGINX serves audio files directly off an NFS-mounted
library; a small `web` service renders the browse UI. Production config
(`docker-compose.yml`, `nginx.conf`) is generated by `bin/gen-config` (run via `make`).

The music library is mounted into the containers either as a host bind mount or, in
production, as a Docker-managed NFS volume (`type: nfs`, `soft,nolock`) pointed at
`truenas.lan:/mnt/data-pool/shared/musics`.

## Player architecture

There is exactly one `<audio>` element, rendered by `components/PlayerBar.tsx` inside
`PlayerProvider` (`lib/player.tsx`), both mounted in `pages/_app.tsx`. `_app` survives
client-side navigation, so playback continues while browsing — **internal links must use
`next/link`**; a plain `<a>` does a full reload and interrupts playback (state is restored
from `localStorage` key `musics.player`, paused at the saved position).

- Song "Play" plays just that song (`continuous=false`); "Play album/all" and playing from
  the queue set `continuous=true`, which auto-advances through the queue.
- "Play album" inserts the rest of the album at the front of the existing queue rather
  than replacing it.
- Audio URLs are `/api/musics/<path>`; nginx's `location ~ /musics/(.+)` regex matches
  anywhere in the URI, so that prefix is served straight off the library.

To try UI changes against the real library without touching prod, rsync changed files to
`linux.lan:~/dev/musics` and run the dev stack there (`cd dev && docker compose up -d
--build`, serves on port 3142, bind-mounts the source with hot reload).

## Production host boot-ordering gate (NFS reboot fix)

**Symptom (fixed 2026-06-05):** After the production host `linux` (Debian 12) rebooted,
containers came back up but the NFS mounts were empty/broken, and the stack had to be
restarted by hand every time.

**Root cause:** Docker named NFS volumes are mounted lazily when the first container
using them starts, and Docker was starting containers before TrueNAS (10.1.1.2) was
actually serving NFS. `docker.service` has `After=network-online.target`, but both
wait-online services are disabled on this host, so that target is a no-op — Docker fired
at `basic.target`, well before NFS was ready. With `soft,nolock` the mount failed fast
and the container came up anyway with an empty mountpoint. A manual `docker compose
restart` worked only because stopping all containers dropped the volume's refcount to 0,
forcing Docker to unmount and then remount once NFS was finally up.

**Fix (host-level, covers every NFS consumer on `linux` — musics, photodirs, and the
`/mnt/shared` fstab mount used by mp3, etc.):** a oneshot readiness gate that blocks
until `rpcinfo` confirms NFSv4 is serving, with a 30s timeout so it can never wedge boot
(worst case = pre-fix behavior). `docker.service` and the `/mnt/shared` mount are both
ordered behind it.

This lives on the host, not in this repo's compose file. Canonical copies of the three
files (reproduce verbatim if rebuilding the host):

`/usr/local/sbin/wait-for-nfs.sh` (mode 755):
```bash
#!/bin/bash
# Boot-ordering gate: block until the TrueNAS NFS server is actually serving
# NFSv4, or give up after a timeout so we can NEVER wedge boot permanently.
set -u
HOST="${NFS_HOST:-truenas.lan}"
TIMEOUT="${NFS_WAIT_TIMEOUT:-30}"
deadline=$(( $(date +%s) + TIMEOUT ))
while ! rpcinfo -T tcp "$HOST" nfs 4 >/dev/null 2>&1; do
  if [ "$(date +%s)" -ge "$deadline" ]; then
    echo "wait-for-nfs: $HOST NFSv4 not ready after ${TIMEOUT}s; continuing anyway" >&2
    exit 0
  fi
  sleep 2
done
echo "wait-for-nfs: $HOST NFSv4 ready"
exit 0
```

`/etc/systemd/system/wait-for-truenas.service`:
```ini
[Unit]
Description=Wait until TrueNAS NFS server is serving (boot-ordering gate)
After=network-online.target nss-lookup.target
Wants=network-online.target

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/wait-for-nfs.sh
RemainAfterExit=yes
TimeoutStartSec=60

[Install]
WantedBy=multi-user.target
```

`/etc/systemd/system/docker.service.d/10-wait-nfs.conf`:
```ini
[Unit]
After=wait-for-truenas.service
Wants=wait-for-truenas.service
```

And in `/etc/fstab`, the `/mnt/shared` line carries
`x-systemd.requires=wait-for-truenas.service` in its options.

Install/redeploy: write the three files, add the fstab option, then
`sudo systemctl daemon-reload && sudo systemctl enable wait-for-truenas.service`.
Verify without rebooting: `systemctl show docker.service -p After | grep wait-for-truenas`.

## Generating production config

`make` runs `bin/gen-config` interactively (web port, bind vs nfs mount, NFS host/path),
writes `docker-compose.yml` + `nginx.conf`, then `docker compose build && up -d`. Defaults
can be saved to a gitignored `.env` (see the `MUSICS_*` vars printed at the end of the run).
